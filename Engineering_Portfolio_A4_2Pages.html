1. 生命週期驅動之解耦軟體架構 (Lifecycle Architecture) arch.op.*

為解決傳統 FTC 單一 OpMode 程式碼臃腫與阻塞（Blocking）問題，我們自主設計了基於觀察者與單例註冊模式（Singleton Global Registration）的底層框架 OpObject 與 OpBehavior：

  • 全域自動掛載 (Zero-Boilerplate Subsystems)：各子系統（Drivetrain、Intake、Flywheel、Yaw、Limelight）於類別載入時透過 OpObject.RegisterGlobalBehavior() 自動註冊，無須在每個 OpMode 重複初始化。
  • 統一生命週期管理：由 OpObject 統一調度 Init() → Start() → Loop() → Stop()，確保所有感測器讀取、PID 控制與致動器輸出皆在同一主迴圈週期內非阻塞（Non-blocking）同步更新。
  • 即時參數熱更新 (Live Tuning)：全系統常數集中於 @Configurable Config.java 與 Constants.java，支援比賽現場透過 Dashboard 即時微調 PIDF 與物理常數，無須重新編譯 APK。

2. 非阻塞平行狀態機與自動階段決策樹 (Parallel Autonomous State Machine) arch.op.behavior.statemachine.*

針對 30 秒自動階段（Autonomous）需要同時執行「底盤貝茲曲線移動、飛輪預熱、機構取放與視覺判讀」之高並行需求，我們研發了支援有向無環圖（DAG）平行分支的狀態機引擎：

  • 一對多平行觸發 (StateObject.Then(StateObject...))：單一狀態完成時可同時啟動多個後續狀態。例如 entryState.Then(new WaitForMillisecond(300), new Shoot(true)) 可在啟動射擊的同時開始非阻塞計時，計時結束後無縫銜接 .Then(new Shoot(false)) 與下一段路徑追蹤。
  • 動態條件分支 (LogicSwitch)：結合 Java BooleanSupplier Lambda 表達式（例如 new LogicSwitch(() -> isPositive, pathPos, pathNeg)），根據場地狀態或 Limelight 視覺辨識結果即時切換路徑。
  • 防並行修改崩潰機制 (Deferred Mutation Queue)：於 StateMachine.Loop() 迭代期間透過 m_isIterating 旗標將新增/移除狀態暫存於 m_statesToAdd 與 m_statesToRemove，徹底杜絕 Java ConcurrentModificationException，並內建獨立 loopIntervalMsec (20ms) 與 timeoutMsec 超時保護。

3. 同軸舵輪 (Coaxial Swerve) 與 Pedro Pathing 導航 pedroPathing.Constants

底盤子系統支援 Coaxial Swerve（四輪獨立轉向同軸舵輪）與 Mecanum（麥克納姆輪）雙模式抽象切換（Config.driveMode），並整合 Pedro Pathing 貝茲曲線追蹤與 goBILDA Pinpoint Odometry：

  • 四組同軸舵輪模組精準校準 (CoaxialPod)：軸距 210 mm × 296 mm，使用絕對類比編碼器（lfenc, rfenc, lbenc, rbenc，電壓範圍 0.001V ~ 3.225V）搭配獨立零點偏移角（43°, 0°, 32.03°, 300°）與前後輪差異化前饋補償（kP=0.3, kD=0.01, kFFront=0.013, kFBack=0.019）。
  • 硬體通訊快取與 X-Lock 防禦：啟用 Motor/Servo CachingThreshold = 0.05 過濾微小重複指令，大幅提升 Control Hub 迴圈頻率；煞車時自動進入 ZeroPowerBehavior.X_LOCK 菱形鎖死姿態抵抗衝撞。
  • Pinpoint 雙輪里程計與跨階段座標交接：配置 goBILDA 4-BAR POD（前向偏移 60.0 mm、橫向偏移 16.6 mm），並透過 AutoBase.savePose 將自動階段結束時的精確場地座標與航向角無縫傳遞至 ManualControl 手動階段。

1. 全場域自適應射控系統核心亮點 subsystem.shooter.*

傳統 FTC 射擊系統依賴固定距離查表法（Lookup Table），一旦機器人偏離預設點或飛輪掉速即無法命中。我們在 ShooterCalculator 與 Flywheel 中研發了五階段全解析彈道物理模型：

  • 任意位置與移動中射擊 (Shoot-on-the-Move)：結合里程計座標、底盤即時速度向量與砲塔偏心矩陣，全場任意座標皆可即時解算三維仰角（Pitch）、偏航角（Yaw）與目標轉速（RPM）。
  • 前饋 (Feedforward) + 反饋 (Feedback) 雙層解耦：前饋層計算滿足 60° 理想入網角的最低能耗初速；反饋層讀取飛輪真實轉速，當轉速因連續射擊微幅下降時，即時反解拋物線二次方程式動態微調伺服仰角，確保彈著點不偏移！
  • 雙參數非理想物理擬合：僅需 2 個物理常數即可完整補償打滑、球體壓縮、空氣阻力與馬格納斯效應（Magnus Effect）。
2. 五階段閉迴路彈道數學推導與演算法實作 (5-Stage Mathematical Pipeline) ShooterCalculator.java & Flywheel.java
階段 I
單飛輪弧形導罩物理轉換 (Hooded Shooter Kinematics)：單飛輪搭配固定弧形外罩（Hood）時，球體中心線速度理論值為飛輪表面切線速度之一半（$v_{\text{th}} = \frac{1}{2}\omega R_{\text{fw}}$）。我們引入能量轉換率 $\eta$ (ENERGY_CONVERSION_RATE = 0.8472) 補償球體壓縮與摩擦損耗，並加上進球機構初速 $v_{\text{in}} = 3\text{ in/s}$： v_exit = (RPM / 60 * 2π * R_fw / 2) * η + v_intake（反向亦支援由目標初速反推 PID 目標轉速 VelocityToRPM()）。
階段 II
砲塔座標旋轉變換與移動射擊補償 (Turret Frame & Shoot-on-the-Move)： (1) 透過二維旋轉矩陣將機器人中心座標轉換為砲塔出球點絕對座標：turretX = x + fwd·cos(ψ) - left·sin(ψ)、turretY = y + fwd·sin(ψ) + left·cos(ψ)； (2) 由前次發射垂直分速度 $v_z = v\cos\theta_{\text{servo}}$ 解算滯空飛行時間 $t_{\text{fly}} = \frac{v_z + \sqrt{v_z^2 - 2gH}}{g}$（取下降段較大正根），並對目標座標進行相對速度向量平移： P_predict = P_target - V_robot * t_fly，並加入 |Y| > 24 in 遲滯區間（Hysteresis）防止機器人在中線 y = 0 附近切換目標時砲塔劇烈擺動。
階段 III
虛擬目標座標變換 — 空氣阻力與 Magnus 效應補償 (Virtual Target Transformation)： 為避免在 Control Hub 上執行高耗時的數值微分方程積分（Runge-Kutta），我們提出虛擬目標點平移演算法：透過單一參數 能量損失率 $k_{\text{loss}}$ (ENERGY_LOSS_RATE = 0.0002) 將水平距離與高度差隨距離平方非線性延展： d' = d * (1 + k_loss * d)，h' = h + k_loss * d²。距離越遠，虛擬目標點 $B'(d', h')$ 自動退後且拉高，完美抵消遠距離空氣阻力造成的提早下墜。
階段 IV
前饋理想初速解算與防撞框演算法 (Feedforward Velocity & Front-Wall Clearance)： 為使球以最佳入射角 $\theta_{\text{inc}} = 60^\circ$ 空心落入目標，由拋物線幾何恆等式推導發射仰角：tan(θ_launch) = tan(θ_inc) + 2h'/d'，並依硬體極限 [36°, 60°] 劃分遠距（精確 $60^\circ$ 入網）、中距（線性平滑插值）與近距三區段，代入 v_ideal = sqrt(g·d'² / (2·cos²θ·(d'·tanθ - h')))。 【防撞框檢查 frontWallDistance】：計算球道與角落目標前牆（距角落 $18.3/\sqrt{2} \approx 12.94\text{ in}$ 之 $45^\circ$ 斜線）交點距離 $d_{\text{fw}}$；若該處球高 $y(d_{\text{fw}}) < H + \Delta h_{\text{clear}}$，演算法自動以 +1° 步進遞增仰角重算初速，確保球體絕對不撞擊目標前緣！
階段 V
真實轉速移動平均濾波與反饋仰角動態微調 (7-Pt Moving Average & Feedback Pitch/Yaw)： 使用大小為 7 的環形緩衝區（Circular Buffer）對編碼器轉速進行移動平均濾波消除量化雜訊，再將真實初速 $v_{\text{actual}}$ 代入拋物線二次方程式： A·tan²θ - B·tanθ + C = 0（其中 $A = \frac{gd'^2}{2v^2}, B = d', C = h' + A$），即時反解物理仰角並轉換為伺服馬達座標 servo_deg = 90° - physics_deg。同時 Yaw.java 以背向正中（180° 偏移、比例 0.00395/deg）即時追蹤 ±177.5° 偏航角。
3. 雙參數 5 分鐘跨場地快速校準標準作業程序 (Field Calibration SOP) Shooter.md

比賽現場更換球體批號、空氣濕度或場地毯面皆會影響彈道。我們將複雜物理模型濃縮為兩步驟、零公式推導的標準化校準流程：

  • SOP 步驟 1（近距離無阻力測試 → 求解硬體傳輸效率 ENERGY_CONVERSION_RATE）：
    將機器人停於距離目標極近處（如 d = 24 in，可忽略空氣阻力），將仰角固定於 45°，微調飛輪轉速至完美空心命中並記下 perfect_rpm。呼叫內建校準函式 ShooterCalculator.calibrateEnergyConversionRate(24, H, perfect_rpm) 自動反算並填入 Config.java（目前實測值為 0.8472）。
  • SOP 步驟 2（遠距離阻力測試 → 求解空氣阻力補償 ENERGY_LOSS_RATE）：
    完成步驟 1 後退至遠距離（d ≥ 72 in）開啟全自動迴圈發射。若球受空氣阻力與 Magnus 效應提早下墜（落於籃框前方），直接於 Dashboard 將 ENERGY_LOSS_RATE 以 +0.001 微調遞增至完美命中（目前實測值為 0.0002），5 分鐘內即可完成全場域曲線擬合！
